1. Introduction 
1.1 Purpose of this Document 
The purpose of this Software Requirements Specification (SRS) document is to provide a detailed
overview of the LOBBY Visitor Management System, its parameters, and goals. This document
describes the project's target audience, user interfaces, hardware and software requirements, and
functional behaviour. It defines how the client, development team, and end users view the product
and its functionality. 
This SRS serves as a contract between the stakeholders and the development team. It establishes
a common understanding of the system requirements and provides a baseline for design,
implementation, testing, and validation activities. 
1.2 Scope of the Development Project 
LOBBY is a web-based visitor management system designed for a college or university campus.
The primary objective is to centralize visitor details, streamline the entry and exit process, and
reduce reliance on manual registers, phone calls, and messaging. 
At present, visitor details are often written in paper registers or managed through informal
communication. This makes it difficult to retrieve historical records and to know which visitors
are currently inside the campus. LOBBY addresses these problems by providing role-based access
for Students/Faculty, Admin, and Security Staff. 
The system shall support the following core capabilities: 
1.   Student or Faculty members can raise visitor requests that are forwarded to Admin for 
approval and, after approval, made available to Security at the gate. 
2.   Security Staff can register direct (walk-in) visitors who arrive without a prior request, 
assign permitted date and time, and extend the allowed duration when necessary. 
3.   When a visitor's allowed time expires and exit has not been recorded, Security and Admin 
receive notifications; the visitor may also receive an alert via message or email. 
4.   Large groups (for example, students from another institution) can submit details in an Excel 
or CSV file. Admin imports the file, reviews the data, and approves the group in a single 
operation. 
5.   Students/Faculty can create temporary visitor codes for regular relatives, valid for a defined 
period, so that repeated data entry is avoided while Security still records each entry and 
exit. 
The main aim of LOBBY is to reduce manual work, maintain accurate visitor records, and make
campus visitor management more efficient and transparent.

2. Overall Description 
2.1 Product Perspective 
LOBBY is a standalone web-based application that runs on campus network infrastructure and is 
accessible through standard web browsers. It is not a component of a larger existing product;
however, it may later integrate with campus identity systems or notification gateways. 
The system operates with three primary user roles interacting through role-specific dashboards: 
•   Student/Faculty   –   initiate visitor requests, create temporary codes, and view request 
history. 
•   Admin   –   approve or reject requests, import group visitor lists, manage users, and view 
reports. 
•   Security Staff   –   verify approved visitors at the gate, register direct visitors, record 
entry/exit, extend time, and validate temporary codes. 
All visitor data, request statuses, entry/exit timestamps, and codes are stored in a central relational 
database. The system requires network connectivity (campus network or internet) for operation.
Notifications (in-app, email, or message) are used to inform stakeholders of status changes and
time-expiry events. 
The product does not rely on specialized hardware such as smart-card readers, biometric devices, 
or automatic barriers in the first version. Visitor identity verification remains a manual process
performed by Security Staff at the physical gate. 
2.2 Product Functions 
The product shall be able to perform the following major operations: 
1.   Authenticate users (Student/Faculty, Admin, Security) and enforce role-based access to 
features. 
2.   Allow Students/Faculty to submit visitor requests with visitor details, purpose, host, 
expected date and time. 
3.   Allow Admin to view, approve, or reject pending visitor requests. 
4.   Make approved requests visible to Security Staff for gate verification. 
5.   Allow Security Staff to record visitor entry and exit times and update visitor status (Inside 
Campus / Exited). 
6.   Allow Security Staff to register direct (walk-in) visitors and assign permitted date and time. 
7.   Allow Security Staff to extend the permitted time of a visitor currently inside the campus. 
8.   Notify Security and Admin (and optionally the visitor) when a visitor's allowed time 
expires without an exit record.

10.   Allow Students/Faculty to create temporary visitor codes with a defined validity period for

11.   Allow Security Staff to verify temporary visitor codes before permitting entry. 
12.   Provide search and history views of visitor records by name, phone number, date, or status. 
13.   Provide basic reports and analytics on visitor numbers, entries, exits, and approvals. 
14.   Allow Admin to manage user accounts and role assignments. 
2.3 User Characteristics 
The system is designed for the following primary user types: 
1.   Student   –   Enrolled student of the institution; expected to have basic computer literacy and 
familiarity with web applications. 
2.   Faculty   –   Teaching or research staff; similar computer literacy expectations as students. 
3.   Admin   –   Authorized administrative staff responsible for visitor request approval, group 
import, user management, and reporting; expected to have moderate proficiency with office 
tools (Excel/CSV) and web dashboards. 
4.   Security Staff   –   Gate personnel responsible for verifying visitors, recording entry/exit, and 
handling direct registrations; expected to have basic computer literacy sufficient to operate 
a web-based dashboard at the gate. 
All users are assumed to be computer-literate enough to use a standard web browser. No 
specialized technical knowledge (e.g., database administration or programming) is required of end
users. The interface shall be simple and role-focused so that Security Staff can perform gate
operations with minimal training. 
2.4 General Constraints, Assumptions and Dependencies 
The following constraints, assumptions, and dependencies apply to the LOBBY system: 
Constraints 
•   The system requires a working internet or campus network connection. 
•   Only authorized users with valid credentials may access visitor information. 
•   Visitor personal information must be protected in accordance with applicable data- 
protection policies. 
•   Excel/CSV files for group import must follow the format supported by the application. 
•   The first version is limited to a single campus.

•   Facial recognition, biometric verification, RFID, and automatic gates are outside the

Assumptions 
•   Students and Faculty will have their own authenticated accounts. 
•   Admin and Security Staff will have authorized accounts with appropriate privileges. 
•   Users will enter correct visitor information to the best of their knowledge. 
•   Student/Faculty requests must be approved by Admin before Security can process them at 
the gate. 
•   Security Staff will physically check visitors at the gate. 
•   Direct visitors can be registered by Security without a prior request.

•   Visitor information will be stored in a persistent database. 
Dependencies 
•   Availability of a relational DBMS for data storage. 
•   Availability of email or messaging gateway for optional visitor alerts (if implemented). 
•   Campus network infrastructure and web server environment.

3. Specific Requirements 
3.1 External Interface Requirements 
The following external interface requirements apply: 
•   The product is a web application accessible via standard modern web browsers (Chrome, 
Firefox, Edge, Safari) on desktop and tablet devices. 
•   The user interface shall be primarily textual and form-based, with tables for lists of requests 
and records. Minimal graphics are required beyond standard UI controls and status 
indicators. 
•   No   specialized   hardware   (smart-card   readers,   biometric   sensors,   or   dedicated   gate 
terminals) is required for the first version. 
•   Sound and animation are not essential; optional browser notifications may be used for real- 
time alerts. 
•   The system shall accept Excel (.xlsx) and CSV file uploads for group visitor import. 
•   Optional integration with email or SMS gateways may be used for visitor time-expiry 
alerts.

3.2.6 Visitor Request and Management Flows 
Student/Faculty Visitor Flow 
Student/Faculty → Request → Admin → Approval → Security → Entry → Exit 
Step 1   –   Raise Request: Student/Faculty enters visitor details, purpose, host, date, and 
expected time. 
Step 2   –   Admin Checks: Request appears on Admin dashboard. 

--- Page 13 ---
Page 13 of 17 
Step 3   –   Approval: Admin approves or rejects. Rejected requests end. Approved requests 
are sent to Security. 
Step 4   –   Security Checks: When the visitor reaches the gate, Security verifies approved 
details. 
Step 5   –   Entry: Security records entry; status becomes Inside Campus. 
Step 6   –   Exit: Security records exit; visit is saved in Visitor History. 
General/Direct Visitor Flow 
Visitor Arrives → Security Registration → Time Allocation → Entry → Exit/Extension 
Step 1   –   Visitor Arrives: Visitor comes to the gate without a prior request. 
Step 2   –   Security Registers: Security enters visitor details into the system. 
Step 3   –   Time is Assigned: Security assigns permitted date and time. 
Step 4   –   Entry: Security records entry; status becomes Inside Campus. 
Step 5   –   Time Expires: When allowed time ends, Security can record exit or extend time. 
Step 6   –   Exit: After the visitor leaves, Security records exit and the record is saved. 
Group Visitor Flow 
Student Group → Excel/CSV → Admin Import → Check → Approval → Security → Entry 
Step 1   –   Details are Shared: Visiting group sends required details in Excel or CSV. 
Step 2   –   Admin Imports: Admin uploads the file. 
Step 3   –   Details are Checked: Admin reviews and corrects as needed. 
Step 4   –   Group is Approved: Admin approves; list becomes available to Security. 
Step 5   –   Security Handles Entry: Security uses imported records to verify and record entry. 
Regular Relative Visitor Flow 
Student/Faculty → Create Code → Set Valid Period → Relative Uses Code → Security 
Verification → Entry/Exit 
Step 1   –   Create Code: Student/Faculty adds relative details and creates a temporary code. 
Step 2   –   Set Valid Period: Creator selects how long the code remains valid. 
Step 3   –   Relative Uses Code: Relative presents the same code for visits during the period. 
Step 4   –   Security Verifies: Security checks code validity before allowing entry. 
Step 5   –   Entry and Exit: Security records each visit's entry and exit. After expiry, the code 
cannot be used. 
3.3 Performance Requirements 

--- Page 14 ---
Page 14 of 17 
•   The system shall support concurrent access by multiple users (Students/Faculty, Admin, 
and Security) without significant degradation under typical campus load. 
•   Ordinary interactive operations (login, submit request, approve, record entry/exit, search) 
should complete within a few seconds under normal network conditions. 
•   Group import of a moderately sized file (e.g., a few hundred rows) should complete within 
a reasonable time (tens of seconds) including validation. 
•   The system shall handle only textual and structured form data; large binary media are not 
required. 
•   Data consistency for entry/exit timestamps and status transitions shall be maintained under 
concurrent gate operations. 
3.4 Logical Database Requirements 
The system requires a relational database to store the following primary entities and relationships 
(logical level): 
•   User   –   account credentials, role (Student/Faculty, Admin, Security), profile information. 
•   Visitor   –   name, contact details, affiliation (if any), and linkage to requests or direct 
registrations. 
•   VisitorRequest   –   requester, visitor details, host/department, purpose, expected date/time, 
status (Pending, Approved, Rejected). 
•   VisitRecord   –   actual entry time, exit time, current status (Inside Campus, Exited, Time 
Expired), permitted time window, linked request or direct registration. 
•   TemporaryCode   –   code value, associated relative/visitor, creator, validity start and end. 
•   GroupImport   –   import batch metadata, source file reference, approval status, linked visitor 
records. 
•   Notification   –   recipient, type (approval, rejection, time expiry), timestamp, read status. 
The database shall support querying by name, phone number, date range, and status for search and 
reporting. Historical visit records shall be retained for audit and history views.

3.5 Quality Attributes 
The product is targeted at Students, Faculty, Admin, and Security Staff. The following quality 
attributes are required: 
Usability:   Role-based dashboards shall present only the actions relevant to each role. Forms and 
lists shall be clear and require minimal training, especially for Security Staff at the gate. 
Reliability:   Entry/exit and status updates shall be recorded reliably; the system should not lose 
visitor records under normal operation. 
Security:   Only authenticated and authorized users may access visitor data. Role-based access 
control shall prevent Students/Faculty from performing Admin or Security actions, and vice versa. 
Maintainability:   The design shall allow future addition of notification channels and optional 
integration points without redesign of core visitor flows. 
Privacy:   Visitor personal information shall be accessible only to authorized roles and protected 
according to institutional policy.

3.6 Other Requirements 
Limitations of the first version: 
•   No facial recognition or biometric verification; identity is checked manually by Security. 
•   The system can indicate when a visitor's allowed time has expired but cannot physically 
compel the visitor to leave. 
•   Group import works only with the supported Excel/CSV format. 
•   Temporary visitor codes cannot be used after their validity period ends. 
•   RFID, automatic gates, facial recognition, and biometric verification are outside the current 
scope. 
•   No additional mandatory requirements are specified at this time beyond those already 
stated.
