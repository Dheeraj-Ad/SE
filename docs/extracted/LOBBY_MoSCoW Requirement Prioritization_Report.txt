Question 1: Identification of Requirements 
Twenty requirements were identified for the LOBBY Visitor Management System, grouped below under
Functional, Non-Functional, User/Stakeholder, and System requirements. 
1.1 Functional Requirements 
•   R2:   Student/Faculty can raise a visitor request with visitor details, purpose, host, date and expected
time 
•   R3:   Admin can view, approve, or reject pending visitor requests 
•   R4:   Security Staff can record visitor entry and exit times and update status (Inside Campus /
Exited) 
•   R5:   Security Staff can register direct (walk-in) visitors and assign permitted date and time 
•   R7:   Authorized users can search visitor records by name, phone number, date or status 
•   R11:   Admin can import group visitor details from Excel or CSV, review and approve the group 
•   R12:   Admin can create temporary visitor codes for faculty with regular entry/exit needs 
•   R13:   Security Staff can verify temporary visitor codes before allowing entry 
•   R14:   Security Staff can extend the permitted visiting time of a visitor currently inside campus 
•   R17:   System provides basic reports and analytics (visitor counts, entries, exits, approvals) 
•   R18:   Visitor receives a message or email alert when allowed time is about to expire or has expired 
1.2 Non-Functional Requirements 
•   R9:   System protects visitor personal information and allows access only to authorized roles 
•   R10:   System requires campus network or internet connectivity for operation 
•   R15:   System notifies Security and Admin when a visitor's allowed time expires without exit 
1.3 User / Stakeholder Requirements 
•   R1:   User login and role-based authentication for Student/Faculty, Admin, and Security Staff 
•   R8:   Role-based dashboards for Student/Faculty, Admin and Security Staff 
•   R16:   Admin can manage user accounts and role assignments

1.4 System Requirements 
•   The system shall store all visitor details, request status, entry/exit timestamps, temporary codes
and related data in a centralized persistent database. 
•   The system shall operate as a web-based application requiring campus network or internet
connectivity.

campus in the first version, while deferring advanced identity and gate-automation features.
